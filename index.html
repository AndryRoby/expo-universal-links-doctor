01 / the pain

Three reasons your universal link opens Safari instead of your app.

Every Expo team hits the same three walls — sometimes all at once, and usually only in a release build, on a real device.
P01 · exact format

ios.associatedDomains must be exactly applinks:domain — no protocol, no path.

A single stray https:// prefix or trailing path on the associatedDomains entry, and iOS silently never attempts the Universal Link at all — no error, it just opens Safari.

format drift
P02 · fingerprint drift

Your assetlinks.json lists the wrong signing certificate.

A local debug keystore, an EAS dev-client build, and a Google Play App Signing release build each have a different SHA-256 fingerprint — only the one that's actually hosted on your domain verifies.

EAS vs. debug keystore
P03 · Expo Go can't do it

Universal Links and App Links don't work inside Expo Go at all.

Both are native-OS features tied to the installed app's bundle ID / signing key. Expo Go is itself the installed app — you need a development build or a standalone build to test either one.

One function. Config in, diagnosis out.

No server, no SDK key, no signup. doctor-universal-links.js is plain JavaScript — read it, fork it, or run it in your own scripts or CI.
doctor-universal-links.js 0 dependencies 
import { diagnose } from './doctor-universal-links.js';
// or, loaded globally: const { diagnose } = window.UniversalLinksDoctor;

const result = diagnose({
  ios:     { bundleId, teamId, associatedDomains, aasaJson, aasaServedWithRedirect, aasaContentType },
  android: { packageName, sha256Fingerprints, assetlinksJson, intentFilters },
  runtime: 'expo-go' | 'dev-build' | 'standalone' | '',

05 / faq

Questions developers actually search for.

Straight answers to the same Universal Links / App Links questions this tool diagnoses — for when you just need the answer, not the checker.
Q01

Why does my universal link open Safari instead of my Expo app?

iOS matches Universal Links against the live apple-app-site-association file and Android matches App Links against assetlinks.json — if either file is missing, unreachable, redirected, or lists a different Apple App ID or package/fingerprint than your actual build, the OS silently falls back to the browser with no error. The most common single causes: an ios.associatedDomains entry with "https://" or a path, a missing autoVerify: true on Android, and a fingerprint in sha256Fingerprints that isn't listed in assetlinks.json.

Q02

Do universal links work in Expo Go?

No. Per Expo's own linking docs, "support for incoming links in Expo Go is limited." Universal Links / App Links verification is a native-OS feature tied to the installed app's bundle ID and signing key — Expo Go is itself the installed app, not yours. Test with a development build (npx expo run:ios / run:android, or an EAS dev-client build) or a standalone/production build instead.

Q03

What is the correct format for ios.associatedDomains in app.json?

Each entry must be exactly "applinks:<domain>" — e.g. "applinks:example.com" — with no https:// prefix and no path after the domain. Expo's docs call this out explicitly as "a common mistake that will result in the universal links not working." List each subdomain as its own entry.

Q04

Why is my Android App Link not verified (assetlinks.json)?

assetlinks.json must be a JSON array (not a bare object) reachable at exactly /.well-known/assetlinks.json, with relation: ["delegate_permission/common.handle_all_urls"], target.namespace: "android_app", and a matching package_name plus sha256_cert_fingerprints. The intent-filter itself also needs autoVerify: true and scheme https — without it Android never attempts verification. Check with adb shell pm get-app-links <package>.

Q05

Which SHA256 fingerprint goes into assetlinks.json for an EAS build?

Run eas credentials -p android, pick the build profile you're testing, and copy the "SHA256 Fingerprint" shown there. A local debug keystore, an EAS-managed dev-client keystore, and a Google Play App Signing release keystore are three different certificates — the single most common App Links failure is hosting the wrong one. If Play App Signing re-signs your release, use the app signing key certificate's fingerprint from Play Console, not your EAS upload key.

Q06

How do I test apple-app-site-association and assetlinks.json?

curl -I https://<domain>/.well-known/apple-app-site-association should return HTTP 200, no redirect, Content-Type: application/json — Apple's fetcher won't follow redirects. On a Mac, swcutil dl -d <domain> shows what Apple's CDN actually cached, and swcutil verify checks one URL against it. For Android, adb shell pm get-app-links <package> shows the verified state directly. Apple caches the AASA per device at install time, so reinstall after changing it rather than assuming an edit takes effect instantly.
